## 1. 目的

短時間で遊べて、親しみやすく、kawaii要素を持つロジックパズルが、プレイヤーの継続プレイを促せるか検証するため、全20ステージのWebプロトタイプを制作する。

広告、収益化、ネイティブアプリ化、大量の問題生成に進む前に、このプロトタイプでゲームループそのものの面白さを検証する。

本書を実装仕様の正本とする。議論元に含まれる検討途中の案と本書が矛盾する場合は、本書を優先する。

## 2. プロダクトコンセプト

### 一言で表すと

> この子たちはちょっぴり神経質。ほかの猫と目が合うと眠れないみたい。みんなが安心できる寝床を見つけよう。

英語版コピー:

> These nervous kitties cannot sleep while another sleeping cat is watching. Find a safe bed for every cat.

### プレイヤーに与える体験

プレイヤーの役割は、抽象的な駒を配置することではなく、猫たちが安心して眠れる場所を見つけてあげることである。対立を避けるゲームではなく、猫を気遣うcozyな体験を目指す。

### 設計目標

- 長い説明を読まなくても、盤面とアニメーションから理解できる。
- 片手で遊べるタップ操作だけで完結する。
- 1ステージを数十秒から数分で遊べる。
- 「候補を消す → 場所が確定する → さらに候補が消える」という推理の報酬を頻繁に発生させる。
- 公開する全ステージに一意解がある。
- 将来、多数の問題を生成・検証しやすい単純なルールにする。

### プロトタイプで扱わないもの

- 広告、課金、アカウント、クラウドセーブ、ランキング、デイリーチャレンジ。
- Android/iOSのネイティブプロジェクト。
- ゲームエンジン、物理演算、3D表現、ドラッグ＆ドロップ操作。
- 実行時のプロシージャル問題生成。
- 一意解にするためだけに追加する数字や特殊ヒント。

## 3. 基本ルール

### 3.1 盤面要素

ゲーム上の意味を持つマスは、次の3種類だけとする。

| 要素 | 意味 | 猫を置けるか | 視線を遮るか |
|---|---|---:|---:|
| 床 | 部屋を構成する装飾・通路 | いいえ | いいえ |
| 寝床 | 猫を寝かせる候補位置 | はい | いいえ |
| 家具 | 壁、棚、観葉植物など | いいえ | はい |

家具の見た目には複数のバリエーションを用意できるが、MVPではすべて同じ視線遮断機能を持つ。

### 3.2 猫の配置とクリア条件

- 猫は寝床にだけ配置できる。
- 各ステージには、寝かせる猫の数 `K` が指定される。
- 猫がちょうど `K` 匹配置され、眠っているどの2匹の猫の間にも視線が通っていなければクリアとなる。
- 猫自身は視線を遮らない。
- 空の寝床とプレイヤーが付けた印は視線を遮らない。
- 猫を置いた順番や、最終的な `×` 印の状態は正解判定に含めない。

### 3.3 視線ルール

- 視線は上下左右にだけ伸びる。
- 斜め方向の視線は存在しない。
- 視線は盤面の端、または最初の家具に到達するまで続く。
- 2つの寝床が同じ行または列にあり、その間に家具がなければ、両方に猫を置いたとき競合する。

例:

```text
🐱  ·  🐱    不正解: 間を遮るものがなく、視線が通る

🐱  🌿  🐱   正解: 家具が視線を遮る

🐱
·             不正解: 縦方向にも視線が通る
🐱
```

### 3.4 間違えたときの扱い

- ライフ、時間ペナルティ、ゲームオーバーは設けない。
- 気軽に試行錯誤できるよう、競合する配置も一時的には許可する。
- 配置済みの猫と競合する寝床もタップでき、猫を配置できる。操作自体は無効化しない。
- 競合している猫と、その間の視線を即座に優しく強調表示する。
- ゲーム側がプレイヤーの `×` 印を自動で追加・削除しない。

## 4. プレイヤー操作

寝床をタップすると、次の順序で状態が切り替わる。

```text
空 → 猫 → × → 空
```

必須操作:

- 一手戻す
- リセット
- ヒント

詳細:

- 配置済みの猫と競合する寝床は薄く表示するが、タップ操作は許可し、自動で `×` は付けない。
- 競合する猫を配置した場合は、猫と視線を赤系の色で強調して理由を示す。
- `×` は正解データではなく、プレイヤー自身が管理するメモとする。
- 「一手戻す」は、印の変更を含む直前のプレイヤー操作を取り消す。
- リセットはステージ開始時の状態に戻す。十分な操作履歴がある場合のみ、確認を表示する。
- 各操作の直後にクリア条件を自動判定する。

## 5. 数理モデルと一意解

各寝床をグラフの頂点として扱う。2つの寝床に猫を置いたとき互いの視線が通る場合、その頂点間に無向辺を張る。正解は、頂点数がちょうど `K` の独立集合である。

ステージが一意解を持つ条件は次のとおり。

```text
競合グラフに、要素数Kの独立集合がちょうど1つだけ存在する
```

一意解かどうかは、猫が配置された寝床の集合だけで判定する。操作順、`×` 印、アニメーション状態、左右対称に見える装飾は無視する。

### ソルバーのインターフェース

```ts
export type CellKind = "floor" | "bed" | "furniture";

export interface Position {
  row: number;
  col: number;
}

export interface Level {
  id: string;
  width: number;
  height: number;
  catCount: number;
  cells: CellKind[];
  initialCats?: Position[];
  title?: string;
}

export interface SolveResult {
  solutionCount: number;
  firstSolution?: Position[];
}

export function solveLevel(level: Level, limit?: number): SolveResult;
export function conflicts(level: Level, a: Position, b: Position): boolean;
```

ステージ検証時は、解を2つ発見した時点で探索を終了してよい。解が2つ以上ある場合は、いずれも同じ不採用結果になるためである。

```text
countSolutions(level, limit = 2):
  すべての寝床から競合グラフを構築する
  各候補頂点について「選ぶ／選ばない」を再帰的に探索する
  次の場合は枝刈りする:
    選択済み頂点数 > K
    選択済み頂点数 + 残り候補数 < K
    次の候補が選択済み頂点と競合する
  解の数がlimitに達したら終了する
```

コミットする全ステージは、次の条件を満たさなければならない。

- マス数が `width × height` と一致する。
- `K > 0` であり、寝床が `K` 個以上存在する。
- 初期配置の猫がある場合、異なる寝床に置かれ、互いに競合していない。
- 解がちょうど1つ存在する。
- 開発用データに期待する正解を保存する場合、その内容がソルバーの解と一致する。

## 6. 難易度モデル

盤面サイズだけで難易度を決めない。次の指標を記録する。

- 寝床数と猫数。
- 競合グラフの密度。
- 最初から確定できる配置数。
- 基準ソルバーが必要とする分岐数。
- 矛盾を発見するまでの最大深度。
- 推理が連鎖する長さ。
- 一見置けそうだが、最終的には不可能になる寝床の数。

人間の推理を基準に、次の難易度を使用する。

| 難易度 | 必要な推理 |
|---|---|
| D0 | ルールの実演、または見ただけで分かる配置 |
| D1 | 1段階の候補除外、または唯一候補の確定 |
| D2 | 1つの寝床を仮定し、残りの猫を置けなくなる矛盾を発見する |
| D3 | 複数段階の矛盾、または連鎖する結果を追う |
| D4 | 複数の仮定が影響し合う。プロトタイプでは限定的に使う |

このゲームで重要なのは先読みである。現在はルール上置ける寝床でも、そこを選ぶと残りの猫をすべて置けなくなる場合がある。

## 7. 全20ステージの進行設計

具体的な盤面は別途作成し、ソルバーの検証を通過したものだけ採用する。次の表は各ステージで与える体験の目標を定義する。

| ステージ | 盤面目安 | 猫 | 目標 | 役割 |
|---:|---:|---:|---:|---|
| 1 | 2×2 | 1 | D0 / 5〜10秒 | 寝床をタップし、すぐに報酬を得る |
| 2 | 2×3 | 2 | D0 / 10〜15秒 | 上下左右の視線を理解する |
| 3 | 2×3 | 2 | D0 / 15秒 | 家具が視線を遮ることを理解する |
| 4 | 3×3 | 2〜3 | D1 / 20〜30秒 | 「今は置けるが、後で詰む」最初の推理 |
| 5 | 3×3 | 3 | D1 | 候補を消す推理を定着させる |
| 6 | 3×4 | 3 | D1 | 最初の短い推理連鎖 |
| 7 | 3×4 | 3 | D1〜D2 | 配置による候補消去から次の猫が確定する |
| 8 | 4×4 | 3 | D2 | 迷いやすい候補を増やす |
| 9 | 4×4 | 4 | D2 | 行と列の視線を組み合わせる |
| 10 | 4×4 | 4 | D2 / 小さな山場 | 適度な難問による達成感 |
| 11 | 3×4 | 3 | D1 / 休憩 | 意図的に簡単な回復ステージ |
| 12 | 4×4 | 4 | D2 | 読みやすさを保った長めの連鎖 |
| 13 | 4×5 | 4 | D2 | より広い範囲を確認する |
| 14 | 5×5 | 4 | D2〜D3 | 初めての深い矛盾検出 |
| 15 | 5×5 | 5 | D3 | 中盤から終盤に向けた理解度確認 |
| 16 | 4×5 | 4 | D2 / 休憩 | 最終区間前の短いステージ |
| 17 | 5×5 | 5 | D3 | 複数段階の依存関係 |
| 18 | 5×6 | 5 | D3 | 密度は高いが視覚的に整理された盤面 |
| 19 | 6×6 | 6 | D3 | 最終問題直前の難問 |
| 20 | 6×6 | 6 | D3〜D4 | 最終問題と最大のクリア報酬 |

難易度には山と休憩を作る。全ステージを単調に大型化・高難度化しない。

## 8. チュートリアルとヒント

### チュートリアル

- ステージ1では寝床を光らせる、またはポインターを表示し、短い指示文を1つだけ出す。
- ステージ2では、2匹の間を結ぶ視線を一度アニメーションで示す。
- ステージ3では、同じ視線が家具によって遮られる様子を示す。
- ステージ4では、本作の核である「残りの猫をすべて置けるか考える」ことを教える。
- ステージ4以降はモーダル形式の説明を避け、盤面構成と任意のヒントで学ばせる。

### ヒント

ヒントでは正解全体を表示せず、論理的に有用な次の一手を1つ説明する。

推奨する文面:

> この寝床を選ぶと、残り2匹を寝かせる場所が足りなくなります。

MVPでは現在の状態と一意解を比較してヒントを作ってもよいが、UI上では可能な限り理由を説明する。ステージごとのヒント使用回数を記録する。

## 9. フィードバックと演出

### ビジュアル方針

- 丸みのあるシンプルな2Dの猫。
- 淡い家具と暖かい部屋の配色。
- 操作対象である寝床を盤面内で最も読み取りやすくする。
- 色の違いだけに依存せず、ゲーム状態を判別できるようにする。
- CSS Gridでレスポンシブに配置し、スマートフォンで押しやすいタップ領域を確保する。
- 初期実装ではCSSを中心とした簡素な仮素材を使用し、ゲームルールと操作感の検証を優先する。
- 正式なイラスト素材への置き換えを想定し、ゲームロジックと見た目の実装を分離する。

### クリア演出

```text
最後の猫を配置
→ 少し間を置く
→ 全員が丸くなる
→ 目を閉じる
→ 小さな「zzz」
→ 柔らかい効果音
→ 次のステージへ進む操作を表示
```

達成感を与えつつ、テンポを損なわない短い演出にする。ステージ20では、通常より長い「Perfect Nap」演出を使用してよい。

## 11. ステージデータ

次は形式を示すための例であり、実際の全ステージには検証が必要である。

```json
{
  "id": "level-03",
```

ステージファイルにはゲームルールを記述し、ピクセル単位の表示位置は含めない。装飾は、将来別のテーマ用メタデータとして関連付けられるようにする。

## 12. テストと品質基準

必須の単体テスト:

- 横方向と縦方向の視線。
- 家具による遮断と境界条件。
- 斜めにある寝床同士は競合しない。
- 猫と空の寝床は視線を遮らない。
- タップによる状態循環、一手戻す、リセット。
- 競合しない猫がちょうど `K` 匹いる場合だけクリアになる。
- 解が0個、1個、複数個の場合にソルバーが正しい結果を返す。
- 全20ステージがそれぞれ一意解を持つ。

プロジェクト作成後に使用するコマンド:

```bash
npm ci
npm test
npm run build
npm run validate-levels
```

CIでは、依存関係のインストール、型チェック、単体テスト、一意解検証、本番ビルドを実行する。

## 13. プロトタイプでの計測

バックエンドがない段階でも、イベントをローカルに記録するか、プレイテスト結果としてエクスポートできるようにする。

### ローカル保存

- クリア済みステージ、現在の進行状況、ステージ別の計測値を `localStorage` に保存する。
- セーブデータには、将来の形式変更に備えてスキーマバージョンを含める。
- プレイテスト結果を個人情報を含まないJSONとしてエクスポートできるようにする。
- 保存データが破損している場合は、安全な初期値へ戻し、ゲームを継続できるようにする。

ステージごとの計測項目:

- 開始とクリア。
- クリア時間。
- 操作回数。
- `×` 印を付けた回数。
- 一手戻す、リセット、ヒントの使用回数。
- 不正な配置・競合が発生した回数。
- リスタートと途中離脱。

プロトタイプで確認すること:

- 初見プレイヤーがステージ3までに視線と家具を理解できるか。
- ステージ4で先読みの必要性に気付けるか。
- どのステージで自発的にプレイをやめるか。
- ステージ11の休憩が継続プレイを回復させるか。
- ヒントが推理方法を教えているか、単に問題を飛ばす手段になっていないか。
- クリア直後に迷わず「次のステージ」を選ぶか。

最初の外部プレイテストで基準値を得るまでは、継続率などに固定の目標値を設定しない。

リポジトリの規約:

- `package-lock.json` をコミットし、CIと新規clone環境では `npm ci` を使う。
- 改行コードはLF、importパスは大文字・小文字を正確に一致させる。
- 生成されたビルド成果物や、OS固有のエディタ設定を保存しない。
- ゲームの動作はすべてプラットフォーム非依存にする。

将来の展開:

```text
共通のReact UI + TypeScriptゲームコア
                  │
                  ├── Web
                  ├── Capacitor → Android
                  └── Capacitor → iOS（Mac + Xcodeが必要）
```

Capacitorは、Webプロトタイプで開発を継続する価値を確認できた後にだけ追加する。

## 15. 実装順序

1. TypeScript、React、Vite、Vitestのプロジェクトを作成し、Node.jsとnpmの入力条件を固定する。
2. ステージとゲーム状態の型を定義する。
3. 視線判定と競合グラフ構築を実装し、テストする。
4. 解の個数を数えるソルバーとステージ検証機能を実装し、テストする。
5. ステージ1〜4を作成して検証する。
6. CSSによる仮素材を使い、盤面UI、タップ状態の循環、競合表示、一手戻す、リセット、クリア処理を実装する。
7. チュートリアル演出とヒント機能を追加する。
8. `localStorage` による進行保存と、プレイテストデータのJSONエクスポートを実装する。
9. スマートフォン縦持ちを優先し、PCにも対応したレスポンシブ表示とアクセシビリティをテストする。
10. ステージ1〜4の操作感と理解度をプレイテストし、必要な仕様調整を行う。
11. ステージ1〜4の検証後、難易度目標に沿ってステージ5〜20を作成・検証する。

### 初期実装の完了条件

最初の実装対象はステージ1〜4までとする。次の条件を満たした時点で、後半ステージの制作へ進む。

- ステージ1〜4がすべて一意解を持つ。
- 初見プレイヤーがステージ3までに視線と家具のルールを理解できる。
- ステージ4で「現在置けるか」だけでなく「残りの猫をすべて置けるか」を考える体験が成立する。
- タップ、競合表示、一手戻す、リセット、ヒント、クリア処理がモバイルブラウザで問題なく動作する。
